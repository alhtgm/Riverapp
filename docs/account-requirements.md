# 要件定義書 — アカウント機能リニューアル（River）

> 大規模リニューアルの第一弾。個人専用の課題管理アプリ River に「学校所属」と「コミュニティ表示名」の概念を追加する。
> 本書はアカウント周りのみを対象とする。テンプレート共有・匿名集計進捗は後続フェーズで別途定義する。

最終更新: 2026-06-29

---

## 1. 背景と目的

現状の River は Supabase Auth に依存した最小構成で、アカウントが保持する情報は **ログイン用メール＋パスワードのみ**。学校・所属・プロフィールの概念が存在しない。

今回のリニューアルでは、将来の「学校コミュニティ／テンプレート共有／匿名集計進捗」の土台として、アカウントに以下を追加する。

1. **1アカウントに2つのメールを別々に登録**
   - 普段使いメアド（ログイン用、Supabase Auth 本体）
   - 学校ドメインのメアド（所属大学の判定用）
2. **コミュニティ表示名**（他人に見える唯一の名前）

---

## 2. 設計方針（重要な決定事項）

これまでの検討で確定した方針。実装時はこれを前提とする。

### 2-1. ログインは「普段使いメアド」で行う
- Supabase Auth の本体メール＝普段使いメアド。ログインIDになる。
- 理由: 卒業後に学校メアドが失効してもログインでき続ける。

### 2-2. 学校メアドは「所属の証明」専用
- ログインには使わない。ドメインから `school_id` を判定するためだけに使う。
- Supabase Auth が標準で本人確認できるのは「ログイン用の1メール」のみ。学校メアドは2つ目のメールなので、本来は自前確認が必要になる。

### 2-3. OTP（所有確認）は今はつけない
- 初期公開は**自分の大学のみ**＝ドメインが1つに限定されるため、なりすましの実害が小さい。
- チャット・DM・個人プロフィール公開が無いため、なりすます動機が存在しない。
- 「めんどくささを極限まで減らす」ことを最優先し、**学校メアドはドメイン形式チェックのみ**で即OKとする。
- ただし将来の逃げ道として `profiles.school_email_verified` カラムだけ用意しておく（今は未使用、常に false）。後で他大学展開して集計が荒れたら、作り直さずに OTP を足して「確認済みの人だけ集計に入れる」へ切り替え可能にする。

### 2-4. 二層のデータ権限（将来に向けた前提）
- 個人の課題データ（subjects/tasks/recurrences）は従来どおり本人のみ（RLS: `auth.uid() = user_id`）。
- `profiles` の `school_email` / `school_id` は本人（と運営）のみ閲覧可。
- 他人に露出するのは `display_name` のみ。

---

## 3. データモデル

### 3-1. 既存（変更なし）
- `auth.users` … Supabase Auth が管理。普段使いメアド＋パスワードハッシュ等を保持。
- `subjects` / `recurrences` / `tasks` … 各 `user_id` を持ち RLS で本人限定。

### 3-2. 新規: `schools`（学校マスタ）
| カラム | 型 | 説明 |
|---|---|---|
| `id` | uuid PK | |
| `name` | text not null | 学校名（例: ○○大学） |
| `created_at` | timestamptz default now() | |

### 3-3. 新規: `school_domains`（許可ドメイン）
ドメイン → 学校の対応表。許可リスト方式。
| カラム | 型 | 説明 |
|---|---|---|
| `id` | uuid PK | |
| `school_id` | uuid → schools not null | |
| `domain` | text not null unique | 例: `s.yourschool.ac.jp`（@より後ろ） |
| `created_at` | timestamptz default now() | |

- 1校が複数ドメインを持つケースに対応するため別テーブルにする。
- 初期は自分の大学のドメイン1行のみ登録。

### 3-4. 新規: `profiles`（アプリ独自のユーザー情報）
| カラム | 型 | 説明 |
|---|---|---|
| `id` | uuid PK, = auth.users.id | 普段使いメアド/パスワードは Auth 側が保持 |
| `school_email` | text | 学校メアド（所属判定用） |
| `school_email_verified` | boolean default false | **今は未使用**。将来 OTP 用に確保 |
| `school_id` | uuid → schools | ドメインから判定して保存 |
| `display_name` | text not null | コミュニティ表示名。他人に見える唯一の名前 |
| `created_at` | timestamptz default now() | |

#### RLS 方針
- 本人のみ自分の `profiles` 行を読み書き可（`auth.uid() = id`）。
- 他ユーザーへの `display_name` 露出は後続フェーズ（テンプレート作者表示等）で、必要な列だけ返すビュー/関数経由にする。`school_email` は決して他人に出さない。

## 4. 画面仕様: アカウント作成（3ステップ）

```
Step 1 ── 基本登録（ログイン用）
  ├ 普段使いメアド   you@gmail.com        ← Supabase Auth 本体・ログインID
  ├ パスワード       ******（6文字以上）
  └ [次へ] → supabase.auth.signUp で確認メール送信（既存の仕組みそのまま）

Step 2 ── 学校メアドの登録（OTPなし・ドメイン照合のみ）
  ├ 学校メアド       taro@s.yourschool.ac.jp
  ├ 入力時に @以降を school_domains と照合
  │    ├ 一致      → school_id を確定、そのまま次へ進める
  │    └ 不一致    → 「未対応の学校ドメインです」と案内（先に進めない）
  └ 追加操作（コード入力など）は無し ← めんどくささ最小化

Step 3 ── コミュニティ表示名
  ├ 表示名          りばー太郎
  ├ 補足表示: 「本名やメールアドレスは他の人に表示されません」
  └ [はじめる] → profiles 作成、タイムラインへ
```

### 補足
- Step 1 完了後、Supabase の確認メール（普段使いメアド宛）は従来どおり送る。
- Step 2/3 は初回ログイン後のオンボーディングとして実施してもよい（`profiles` 未作成なら強制表示）。実装方式は任意だが、`profiles` が無いユーザーはタイムラインに入る前に Step2/3 を完了させること。
- 既存ユーザー（リニューアル前に登録済み）にも、次回ログイン時に Step2/3 を促す。

---

## 5. バリデーション

| 項目 | ルール |
|---|---|
| 普段使いメアド | メール形式。Supabase Auth が一意性を担保 |
| パスワード | 6文字以上（既存仕様踏襲） |
| 学校メアド | メール形式 かつ @以降が `school_domains` に存在すること |
| 表示名 | 必須。1〜30文字程度。前後空白トリム |

## 6. スコープ

### 今回やる
- `schools` / `school_domains` / `profiles` テーブルと RLS の追加
- アカウント作成の3ステップ画面（Step2 はドメイン照合のみ）
- 自分の大学のドメイン1件を `school_domains` に登録
- `school_email_verified` カラムの確保（未使用）

### 今回やらない（後続フェーズ）
- 学校メアドの OTP 本人確認
- テンプレート共有・取り込み
- 匿名集計進捗（提出率など）＋ k-匿名しきい値
- コミュニティの交流機能（掲示板・チャット等）

---

## 7. 将来拡張の前提メモ
- 集計を導入する際は `tasks.source_template_id`（取り込み元テンプレートとの紐付け）と k-匿名しきい値（例: 5人未満は非表示）を前提に設計する。
- 集計は生データを見せず、数値のみ返す集計専用の経路（ビュー/Edge Function）に限定する。
- 集計が荒れてきたら `school_email_verified` を有効化し、確認済みユーザーのみ集計対象にする。
